## 一、为什么不给「准确率 %」

1. **覆盖率**——我们到底有没有给出时刻；

## 六、已知残留与下一步

### 6.1 有意保留：裸小数仍会误报（4 条）

· `0点一` → 2025-01-21 00:00
· `零点五` → 2025-01-21 00:00
· `零点一。` → 2025-01-21 00:00
· `二十点六` → 2025-01-21 20:00

为什么本轮不修：`零点` 本身是合法时刻（「零点准时抢」→ 00:00），仅凭「点后跟单个数字」
无法区分 0.5 与 0:05，硬加规则会误杀真时刻，需要「点后跟量词/单位」这类更强的上下文信号。
带单位或算术语境的写法（`调高24点5度`、`减八点八`、`升高10点五度`、`一点都不好玩`）已全部掩蔽，不会误报。

### 6.3 不可比样本（3 条）

双方都给出了时刻，但公历日不同（多为「已过期顺延」与语料基准日不一致），无法直接比墙钟，仅供参考。

### 6.4 语料结构限制

338 条中 288 条为「日期粒度区间 / 多候选 / 纯日期 / 世纪 / 无标注」（如「这周」「周五去北京的机票」），与闹钟场景不同构。
可做严格比较的样本仅 46 条（绝对钟点 38 + 相对时长 8），因此本报告只给覆盖与 badcase 清单，不给准确率——任何「准确率」对这张语料都会失真。

### 6.5 下一步建议

1. 补「过 / 差」表达（`十点过六分`、`十点差五分`）——改动小、直击口语。
2. 裸小数误报需要更强的上下文信号（后面跟量词/单位），优先级最低。
3. 语料侧若要评价精度，需先把它改造成「闹钟语义」（+08 基准 + 单点钟点），本报告不背这个包袱。
