## 一、为什么不给「准确率 %」

语料的 `datetime_result` 是 **UTC 语义**（基准 `metadata` 也是 UTC），本产品的闹钟一律落在用户时区（缺省 `Asia/Shanghai`，UTC+08）。
两边基准相差 8 小时，硬算准确率只会得到一个被系统偏移污染的数字。因此这里只统计：

1. **覆盖率**——我们到底有没有给出时刻；
2. **badcase 分类**——把「该给没给」「给了但可疑」「给了且对得上」分开列，供人看。

## 六、已知残留与下一步

本轮（第一阶段）**有意保留**、留待后续处理的项——不是新发现的 bug：

1. **裸小数仍会误报**（`0点一`、`零点五`、`零点一。`、`二十点六`，共 4 条）。
   原因：`零点` 本身是合法时刻（「零点准时抢」→ 00:00），仅凭「点后跟单个数字」无法区分 0.5 与 0:05，硬加规则会误杀真时刻。
   已覆盖的部分：带单位或算术语境的写法（`调高24点5度`、`减八点八`、`升高10点五度`、`一点都不好玩`）已全部掩蔽。
2. **相对时长的复合写法**仍缺（`2小时18分钟以后提醒我。`、`一个半小时后叫我`，共 2 条）：
   `再过十分钟`（无「后」字）、`2小时18分钟以后`（复合时长）、`一个半小时后`（倍数时长）——当前只识别最后一个「N分钟/小时 + 后」。
3. **时段词「中午」未做 +12 校正**（`中午一点`）：`中午一点` 得到 01:00，期望 13:00。
   `下午/晚上/夜里` 已做 +12，`中午` 只处理了 12 点整；需按「中午 1~3 点 → +12」收口（会影响 `中午11点` 这类），故本轮不动。
4. **无分隔符钟点**未支持：`明天早上0900`、`7月19号830`（口语常见，建议按「3~4 位数字 HHMM」收口）。
5. **「过 / 差」表达**未支持：`十点过六分`（10:06）、`十点差五分`（09:55）。
6. **语料结构限制**：338 条中 288 条为「日期粒度区间 / 多候选 / 纯日期 / 世纪 / 无标注」（如「这周」「周五去北京的机票」），与闹钟场景不同构。
   可做严格比较的样本仅 42 条（绝对钟点 36 + 相对时长 6），因此本报告只给覆盖与 badcase 清单，不给准确率——任何「准确率」对这张语料都会失真。

下一步建议顺序：先补 2（相对时长复合）与 3（中午校正）——这两项最贴近真实用户说法，改动也小；
再补 4（无分隔符钟点）、5（过/差）；裸小数（1）需要更强的上下文信号，优先级最低。
