闹钟 Agent · iOS App 落地实现方案

把现有 Web 闹钟升级为可在 App Store 上架、且「关 App 也响」的 iOS 应用。本文基于已核实的 iOS 平台约束给出分阶段、可执行的实现路径。

版本 v1.0（落地稿） 　适配现状：nlu.js 解析引擎 / index.html UI / server.js 推送服务端

核心结论（先看这里）

iOS 上的「网页闹钟」和「App 闹钟」是两套完全不同的通知机制。现有 server.js 的 Web Push（VAPID + web-push）在 iOS 原生壳里完全无效——Apple 规定 WKWebView 不提供 Service Worker / Push API，Web Push 仅在「添加到主屏幕的 PWA」里可用（iOS 16.4+）。因此 iOS App 必须改用：本地通知（主力，关 App 能响、无需服务器） + 可选 AlarmKit（iOS 26+，绕过静音的系统级闹钟） + 可选 APNs（云端同步/远程触发）。推荐技术栈：Capacitor 原生壳封装现有 Web 资产，解析引擎零改动原样跑在 WebView 内。

一、iOS 平台硬约束（已核实，方案不可绕开）

约束事实对闹钟 App 的影响
WKWebView 无 Web Push Capacitor/Cordova 封装的 App 用 WKWebView，不提供 Service Worker / Push API。iOS 16.4+ 的 Web Push 只在使用 Safari「添加到主屏幕」的 PWA 中生效，App Store 壳内无效。 致命 现有 server.js 的 Web Push 在 App 内不能用，必须换本地通知 / APNs。
本地通知 64 限额 UNUserNotificationCenter 每 App 仅保留未来最近的 64 个 pending 本地通知，超出静默丢弃、无错误回调；重复通知计 1 个。 重要 必须做「滑动窗口」：只排未来最近的 N 个，App 每次回到前台重排。
静音模式不响 普通本地通知在 iOS 静音/专注模式下默认不发声。要做到「静音也响」需 Critical Alert 授权（Apple 特殊 entitlement，审核严格）或 AlarmKit（iOS 26+，委托系统时钟 App）。 体验天花板 这是 iOS 闹钟最大痛点，方案必须正面应对（见第三节）。
自定义铃声限制 本地通知自定义声音文件须 ≤30s、aiff/wav/caf 格式、放在 App bundle 顶层（不能子目录），否则静默回退默认音。 注意 丰富铃声需预置并打包，不能运行时动态下载后即时播放。
iOS 版本碎片化 AlarmKit 仅 iOS 26+（2025-09 发布）。大量设备仍跑老系统，需优雅降级到本地通知。 注意 强提醒功能要做版本探测与降级。

二、技术选型对比

路线做法闹钟可靠性工作量结论
纯 PWA
（不进 App Store）		 现有 index.html + Safari「添加到主屏幕」。已支持 iOS 16.4+ Web Push。 可用 但 Web Push 需用户手动「添加到主屏幕」、且仍受静音限制。 极小 不是「App」，不满足上架诉求，仅作过渡。
Capacitor 原生壳
（推荐）		 用 Capacitor 把 Web 资产包成真正的 iOS App；通知走本地通知 / AlarmKit / APNs。 可靠 本地通知关 App 能响；AlarmKit 可绕过静音。 中（1.5–2.5 周） 推荐 复用 90% 现有代码，可上架。
原生 Swift 重写 全部用 SwiftUI + 原生 UI 重写，解析引擎用 JS Core 或直接重写成 Swift。 最可靠 完全掌控通知/铃声/UI。 大（4–6 周+） 过度投入，除非要做极致体验或上架被拒。

三、推荐架构（分层通知，按可靠性递进）

用户界面层（WebView，复用现有代码，几乎零改动）

index.html（解析 UI / 列表 / 澄清）

原样作为 Capacitor Web 资产；运行时检测 Capacitor 环境，隐藏「云端推送」卡片，改用本地通知。

nlu.js（解析引擎）

纯 JS，原样在 WebView 内运行，闹钟时间本地计算，无需联网。

通知策略层（原生桥接，关键改造点）

① 本地通知（主力）

@capacitor/local-notifications。关 App 能响、无需服务器。受 64 限额 + 静音限制。

② AlarmKit（iOS 26+ 增强）

@capgo/capacitor-alarm。把「强提醒」闹钟委托系统时钟 App，绕过静音。需版本探测降级。

③ APNs（可选·云端）

复用 server.js 调度逻辑，将 web-push 替换为 apn 库（或 FCM 转发），支持跨设备/远程触发。

原生底座

Capacitor iOS 工程

Swift 原生壳 + WKWebView；桥接插件连接 Web 层与通知策略层；64 限额滑动窗口管理在原生侧做最稳。

静音问题怎么破（必须决策）
  • 方案甲（推荐起步）：只做本地通知 + 明确告知用户「静音时可能不会响」，引导用户在系统里为该 App 开启「重要警报」或关闭静音。实现最快，覆盖绝大多数场景。
  • 方案乙（强提醒）：iOS 26+ 用 AlarmKit 把闹钟委托给系统时钟 App（绕过静音、最可靠），老版本降级本地通知。需处理 AlarmKit 的「跳转到系统时钟」交互。
  • 方案丙（Critical Alert）：向 Apple 申请 Critical Alert entitlement，普通通知也能静音响。审核严格、通过率低，且需在隐私政策中说明。仅在对可靠性有硬要求时走。

四、分阶段实现计划

Phase 0 · 决策与脚手架（0.5 周）

  • 定通知策略：在甲/乙/丙 中选（建议甲起步，预留乙接口）。决定要不要做云端同步（影响是否引入 APNs）。
  • 环境准备：Mac + Xcode（免费即可跑真机调试；上架需 $99/年 开发者账号）。Node 22 已就绪。
  • 初始化 Capacitor： 
    # 在 alarm_agent 目录内
npm install -D @capacitor/cli
npm install @capacitor/core @capacitor/ios
npx cap init alarm-agent com.yourorg.alarmagent --web-dir .
npm install @capacitor/local-notifications
# iOS 26+ 强提醒（可选）
npm install @capgo/capacitor-alarm
npx cap add ios
npx cap sync

Phase 1 · 封装与通知桥接（1–1.5 周）

  • Web 资产就位：把 index.html 及内联引擎放进 Capacitor web-dir（即项目根）。确保无外部 src 依赖、无 file:// 假设。
  • 环境探测与 UI 适配：在 index.html 应用脚本里加 if (window.Capacitor) { /* 隐藏云端推送卡片，改走本地通知 */ }；保存闹钟时调用本地通知桥接而非 Web Audio/Notification。
  • 通知桥接（关键）：把 computeNextTrigger(a) 的结果转成 LocalNotifications.schedule()。示例： 
    import { LocalNotifications } from '@capacitor/local-notifications';

async function scheduleAlarm(a) {
  // a = 解析结果 {timestamp(秒), label, recurrence, ...}
  const fire = new Date(a.timestamp * 1000);
  await LocalNotifications.schedule({
    notifications: [{
      id: hashId(a),                         // 稳定 id，便于取消/重排
      title: '闹钟',
      body: a.label || '提醒时间到了',
      schedule: { at: fire, allowWhileIdle: true },  // 重复类用 repeats/on
      sound: 'alarm.wav',                    // ≤30s，放 bundle 顶层
      extra: { recurrence: a.recurrence }
    }]
  });
}
// 取消：LocalNotifications.cancel({ notifications:[{id}] })
  • 64 限额滑动窗口（必须）：只在原生侧（最稳）或 Web 侧保留未来最近 ≤60 个到期闹钟的 pending 通知；App 每次 appDidBecomeActive / Web 的 visibilitychange 触发重排： 
    // 思路：取所有启用闹钟，按下次触发时间升序，只 schedule 前 60 个，
// 其余标记为「窗口外」，下次重排时再补。重复闹钟计 1 个，不占额度。
async function rescheduleWindow() {
  const all = getEnabledAlarms().sort((a,b)=>nextAt(a)-nextAt(b));
  const keep = all.slice(0, 60);
  const pending = await LocalNotifications.getPending();
  const keepIds = new Set(keep.map(hashId));
  const drop = pending.filter(p => !keepIds.has(p.id));
  await LocalNotifications.cancel({ notifications: drop.map(id => ({id})) });
  for (const a of keep) await scheduleAlarm(a);
}
  • 本地持久化：现有 localStorage 在 Capacitor 内仍可用（WKWebView 配额），闹钟数据与「已排程」状态本地保存即可。
  • 铃声与交互：预置 1–2 个 ≤30s 的 wav/caf 音效放 iOS bundle 顶层；用 registerActionTypes 注册「贪睡 / 完成」按钮（localNotificationActionPerformed 监听）。

Phase 2 · 真机调试与上架（1 周）

  • 真机跑通：npx cap open ios → Xcode → 连 iPhone → 签名（个人账号可真机调试）→ 验证：关 App 后到点收到本地通知、贪睡/完成按钮可用、64 限额重排正确。
  • 上架物料：App ID、发行证书、Provisioning Profile；App 图标（含 apple-touch-icon）、隐私政策 URL、权限说明文案（通知用途）。
  • TestFlight 内测：邀请少量用户验证不同 iOS 版本（重点看 iOS 26 AlarmKit 与老版本降级）。
  • App Store 审核：闹钟类 App 需清晰说明通知用途；若用 Critical Alert 须在审核备注说明必要性。

Phase 3 · 增强（可选，按需）

  • AlarmKit 强提醒：iOS 26+ 用 @capgo/capacitor-alarm 的 createAlarm 把「强提醒」类闹钟委托系统时钟 App，提供「静音也响」；版本探测，老系统降级本地通知。
  • 云端同步 + APNs：若做跨设备，server.js 保留调度逻辑，将 web-push 替换为 apn 库（需 APNs 认证密钥 .p8）；复用现有 computeNext。手机端 register 上报 device token。
  • Widget / 实时活动：主屏幕 Widget 显示下次闹钟；实时活动显示倒计时（iOS 16+）。

七、风险与缓解

风险等级缓解
静音模式不响高甲：引导用户开启重要警报；乙：iOS 26+ AlarmKit 绕过静音；丙：申请 Critical Alert（难）。建议甲起步 + 预留乙。
64 限额导致远期闹钟丢失中滑动窗口 + 每次回到前台重排；重复闹钟计 1 个不占额度；UI 提示「超过 60 个仅保证最近生效」。
WKWebView 无 Web Push高App 内不依赖 Web Push；改本地通知/APNs。Web 版（PWA）仍可保留 Web Push 作为独立形态。
自定义铃声受限低预置 ≤30s 音效打包进 bundle；不支持运行时动态音效。
iOS 版本碎片化低运行时探测 getOSInfo().supportsNativeAlarms；老版本降级本地通知。
审核被拒（通知/隐私）中清晰权限文案、隐私政策、TestFlight 充分自测后再提交。

九、需要你拍板的决策点

  1. 通知策略：选甲（本地通知 + 引导）/ 乙（AlarmKit 强提醒）/ 丙（Critical Alert）？建议甲起步、预留乙。
  2. 是否做云端同步：只做单机版（Phase 1 即可，最简单），还是跨设备（需 Phase 3 APNs + server 改造）？
  3. 上架范围：先上架中国区 App Store，还是全球？影响合规与隐私政策语言。
  4. 机器资源：是否有 Mac + iPhone 真机？（无 Mac 无法出 iOS 包，这是硬门槛。）
