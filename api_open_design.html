⏰ 闹钟 Agent · 开放 API 设计文档

版本 v1.0 · 状态：设计评审稿 · 范围：仅解析接口 · 鉴权：API Key

一句话定位

把"一句话自然语言"变成"结构化闹钟时间 JSON"。规则引擎优先（高置信度零成本），仅长尾歧义走 LLM 兜底。v1 只开放 POST /v1/parse 与 GET /v1/health，无状态、不碰存储，是风险最低、价值最高的第一步。

1. 范围与边界

v1 开放 POST /v1/parse — 自然语言 → 闹钟时间 JSON

v1 开放 GET /v1/health — 健康检查

暂不开 闹钟 CRUD、Web Push 订阅、多租户持久化（见路线图 Phase 2/3）

现有内部接口 /api/vapid · /api/register · /api/alarm · /api/parse 保留给本地 MVP 网页使用，与对外 /v1/* 互不干扰。

2. 架构

第三方应用 / SDK
      │  Authorization: Bearer <API_KEY>
      ▼
┌─────────────────────────────────────────┐
│  API 网关层（server.js 新增中间件）        │
│   · API Key 校验 + 租户解析                 │
│   · 限流（令牌桶，按 key 60/min）           │
│   · 入参校验（text ≤200 字、JSON 体积）      │

│   ├─ 规则命中(conf≥0.85) → 直接返回 source=rule │

v1 全链路无数据库：解析是纯函数，鉴权只需要一份"有效 Key 清单"。

3. 认证：API Key 模型

3.1 调用方式

所有 /v1/* 请求（/v1/health 除外）必须在请求头携带：

Authorization: Bearer <API_KEY>

3.2 密钥发放（自托管方案）

最小实现用一份 keys.json（或环境变量 ALARM_API_KEYS）保存密钥与配额：

[
  { "key": "ak_live_xxxx", "name": "演示应用", "active": true, "rate_limit": 60 },
  { "key": "ak_test_yyyy", "name": "测试",     "active": true, "rate_limit": 20 }
]

生产环境应改为 DB 存储 + 管理后台发放；密钥泄露可即时 active:false 吊销。

注意："开放"≠"匿名"。即便解析是无状态的，也需 Key 以便限流、配额、审计与滥用追踪。

4. 端点规范：POST /v1/parse

4.1 请求体

字段类型必填说明
textstring✅自然语言输入，≤200 字
timezonestring—IANA 时区，默认 Asia/Shanghai
nowstring(ISO)—可选，覆盖"当前时间"用于确定性测试/回放

4.2 成功响应（200，注意 success 可能为 false）

字段与现有引擎一致，并新增 source 与 request_id：

字段说明
success是否解析出时间
raw原始输入
sourcerule（规则）或 llm（兜底）
alarm时间对象：timestamp(Unix秒) / datetime(ISO) / date / time / recurrence / timezone / lead_minutes / label / enabled
confidence0~1 置信度
needs_clarificationtrue 时需追问
ambiguities澄清提示数组
clarification聚焦追问：type / question / suggestions（v1 引擎新增）
request_id排障用唯一 ID
设计要点：接口"成功"（HTTP 200）≠ 解析成功。模糊输入（如"待会提醒我喝水"）返回 HTTP 200 + success:false，由调用方决定是否发起追问，或由客户端用 clarification.suggestions 引导用户。

5. 错误码与限流

HTTPcode触发场景
400bad_request缺少 text / 超长 / JSON 非法
401invalid_api_key缺头或 Key 不存在
403key_disabledKey 被禁用
429rate_limited超过该 Key 的速率上限
500internal服务端异常

限流：令牌桶，默认每 Key 60 次/分钟（可在 keys.json 按 Key 覆盖）。超限返回 429，建议客户端指数退避重试。

错误响应体：

{ "error": { "code": "invalid_api_key", "message": "API Key 无效或已禁用" }, "request_id": "req_01HX..." }

6. 调用示例

cURL

curl -X POST https://your-domain.example.com/v1/parse \
  -H "Authorization: Bearer ak_live_xxxx" \
  -H "Content-Type: application/json" \
  -d '{"text":"明天早上8点叫我起床"}'

JavaScript（fetch）

const r = await fetch('/v1/parse', {
  method: 'POST',
  headers: { 'Authorization': 'Bearer ' + API_KEY, 'Content-Type': 'application/json' },
  body: JSON.stringify({ text: '30分钟后提醒我开会' })
});
const data = await r.json();
if (data.success) console.log(data.alarm.timestamp);

Python（requests）

import requests
resp = requests.post('https://your-domain.example.com/v1/parse',
    headers={'Authorization': 'Bearer ak_live_xxxx'},
    json={'text': '下周一9点半开会'})
print(resp.json())

7. 版本与兼容性

  • 路径前缀 /v1 即版本号；破坏性变更升 /v2，旧版本至少保留 6 个月并公告。
  • 响应字段新增为向后兼容；移除/改义字段走主版本升级。
  • success:false + 澄清语义在 v1 已稳定，调用方应据此实现追问 UX。

8. 安全基线

  • HTTPS only：API Key 明文传输，必须 TLS；Caddy 自动证书已在脚手架中。
  • CORS：仅对受信任域名开放（不 blanket *）。
  • 输入限制：text ≤200 字、请求体 ≤4KB，防滥用。
  • 审计：每个请求落 request_id + Key 名，便于追溯异常调用。
  • 密钥管理：支持即时吊销；生产环境密钥入库、禁止明文提交仓库。

10. 与现有内部接口的关系

对外 /v1/parse 与内部 /api/parse 共用同一套 parseAlarm 引擎，只是前者增加了鉴权/限流/标准化错误/request_id。实现时建议把内部 /api/parse 也改走统一中间件，避免两套鉴权逻辑。

文档与规范可与 alarm_requirements.html（产品需求文档）互为补充：需求文档讲"产品形态"，本设计文档讲"对外集成契约"。
