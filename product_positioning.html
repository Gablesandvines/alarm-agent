闹钟 Agent · 产品定位决策文档

版本 v1.0（决策稿）｜ 日期 2026-10-12 ｜ 目的：在三种产品形态中选定主角，消除定位漂移
一句话结论：你不是"没东西"，而是同一份引擎被同时往三个方向拉——消费 App、开发者 API、嵌入技能。 真正值钱且难复制的资产是 nlu.js（中文自然语言→结构化时间，56 例回归锁死、规则+LLM 兜底、会反问）。 本决策文档的目标，是帮你在 A / B / C 中选一个主角，其余降级为衍生物。

1. 问题陈述：为什么"没想好怎么体现"

回看已落地的产物，项目实际发出了三种产品信号，而非一个统一形态：

A 消费级工具（C 端）

最初的「中文闹钟 Agent Web 应用」，index.html PWA + 闹钟列表 + 澄清对话 + Web Push。刚又问了 iOS App。

B 开发者 API（B 端）

后来加的开放 API：/v1/parse + API Key + 限流 + CORS + OpenAPI + 密钥管理 CLI（Phase 1 已完成）。

C 嵌入技能

你并行做的「旅游规划 Agent」本可把"到点提醒"当作子能力调用——形态上是内部工具，不单独见用户。

定位漂移的实锤：早期需求文档把项目定位为「纯工具、无服务端、低成本」。但开放 API 已经引入服务端 + 密钥体系， 项目在悄悄往"平台"方向漂。这份文档首先要回答：到底是守住"纯工具"，还是拥抱"服务端平台"？

2. 资产盘点：护城河到底是什么

以下每一项都"贵"且"难抄"，是决策的依据：

  • 中文时间解析引擎 nlu.js：中文数字 / 相对 / 绝对日期 / 星期（含"下周6"数字星期）/ 时段词 / 每 X 天 / 隔周 / 节假日（春节端午中秋）/ 提前提醒 / 多轮澄清。
  • 56 例回归测试：相对时间校验、不随时间过期，已多次堵住"语义边界"类 bug。
  • 规则优先 + LLM 兜底：置信度≥0.85 零成本直接返回，长尾口语才走 LLM——成本结构天然优于纯 LLM 方案。
  • 双形态已验证：同一引擎既跑在浏览器（PWA），又跑在 Node（API），复用度 90%+。

而 UI、推送、API 外壳都是 commoditized（大厂/开源可瞬间复制）。护城河 = 引擎的语料积累与确定性，不是外壳。

3. 三种产品形态详解

A 消费级 App（C 端）

目标用户中文手机用户，想要"说一句话就设好提醒"的体验。
形态iOS / Android 原生壳（Capacitor 封装现有 Web 资产，复用 90% 代码）；单机版用本地通知，云端版加 APNs。
核心卖点「会对话的闹钟」——模糊输入反问并记住上下文（澄清对话）。
关键约束iOS 静音不响（需重要警报/AlarmKit/Critical Alert）、64 个 pending 通知限额、App Store 审核、必须 Mac+iPhone 真机。
已实现Web 端 MVP、澄清 UI、iOS 落地方案文档。
待做Capacitor 封装、本地通知桥接、64 限额滑动窗口、真机上架（2.5–3 周）。
贴合原"纯工具"定位（单机版可零服务端）市场拥挤变现难

B 开发者 API（B 端）

目标用户做日程 / 提醒 / 日历 / 助理类应用的开发者，不想自己造时间解析。
形态/v1/parse + clarification JSON（让别的 Agent 也能多轮追问）+ 按 key 计费 + 文档/SDK。
核心卖点「agentic 时间解析」——别人用 LLM function calling 按 token 花钱，你规则引擎零成本、确定、可离线。
关键约束需服务端（与"纯工具"原定位冲突）；要运维、限流、监控、密钥管理；面临大模型厂商的潜在替代。
已实现Phase 1：鉴权 / 限流 / CORS / 标准错误 / OpenAPI / 集成测试 14/14 通过。
待做Phase 2 闹钟 CRUD + 多租户 DB（SQLite/Postgres，2–3 周）；Phase 3 对外开放 Web Push。
毛利高维护轻最贴"Agent"品牌需服务端

C 嵌入技能 / 白标

目标用户你自己的其他 Agent（如旅游规划 Agent 的"到点提醒行程"）。
形态内部工具 / 技能，作为主 Agent 的一个 tool 调用，不单独面对终端用户。
核心卖点组合拳——丰富主产品的"时间感知"能力。
关键约束无独立市场与营收；价值是间接的（提升主 Agent 体验）。
建议不宜单独做，应作为 A 或 B 的衍生物存在。

5. 核心张力：原定位 vs 现实漂移

原定位（需求文档 v0.1）：纯工具、无服务端、低成本 → 这条线索其实指向 A 单机版（本地通知，零后端，最贴合"低成本"）。
现实漂移：开放 API 已引入服务端+密钥 → 这条线索指向 B。
决策含义：若你想守住最初意愿，应选 A 单机版（可完全无服务端）；若你认可"服务化"价值，选 B。两者不可在叙事上含糊并存。

6. "Agent" 品牌如何立住

立脚点是澄清对话（模糊时反问并记住上下文再解析），它在两种形态里语义不同：

  • 在 A 里：是"体验亮点"——用户说"待会提醒我喝水"，App 反问"30 分钟后？"，补全后解析。
  • 在 B 里：是"契约"——clarification JSON 让别人的 Agent 也能多轮追问，天然 agentic，最贴品牌。

无论选哪条，把"会反问"作为核心叙事，就能区别于普通闹钟/普通解析库。

7. 推荐组合策略（两条候选路线）

路线 ①（推荐）：B 为主角，A 作参考实现

逻辑：最大化护城河（引擎）+ 最高毛利 + 最快上市 + 最贴"Agent"。把 A 做成官方参考 App / Demo（证明引擎在真实消费体验里成立，可当获客/ Loss-leader），但不作为营收主力。

  • 立即：Phase 2（闹钟 CRUD + 多租户 DB）+ 计费 + 开发者文档站。
  • 并行：用 Capacitor 把现有 Web 包成参考 App（满足你的 iOS 兴趣，且零额外引擎成本）。
  • C 自动成立：旅游规划 Agent 直接 /v1/parse 调用。

路线 ②：A 单机版为主角，B 暂缓

逻辑：若你的真实目标是"做一个用户真正在用的好闹钟"、且想守住'纯工具低成本'原定位。选 Capacitor + 本地通知（零服务端），不做后端，不做 API 商业化。

  • 立即：Capacitor 封装 + 64 限额滑动窗口 + 通知策略（重要警报起步，预留 AlarmKit）。
  • B 仅保留已完成的 Phase 1 作为"免费彩蛋"，不投入商业化。
  • 风险：市场拥挤、变现难，但成本也最低、最贴合初心。

8. 决策 Checklist（帮你拍板）

  • 你的目标是用户体感还是可规模化生意？（体感→A；生意→B）
  • 是否接受"服务端 + 密钥"体系？（接受→B；拒绝、想纯工具→A 单机版）
  • 手上有 Mac + iPhone 真机吗？（做 A 的硬门槛；B 不需要）
  • 上架中国区还是全球？（影响合规与隐私政策语言）
  • 通知策略选 重要警报 / AlarmKit / Critical Alert 哪种？（决定 A 的"静音也响"能力）
