闹钟 Agent · Web 应用需求设计与评估

用自然语言一句话设置闹钟：理解时间、返回结构化 JSON、并在到点时可靠提醒。本文档梳理需求、给出技术方案与可行性评估，并附可交互原型。

场景 #17 · Agent 应用 形态：Web / PWA 核心：NL → 时间 → JSON 版本 v1.0（路线图已对齐）

一、项目概述

目标：用户用日常口语即可设置闹钟，例如「明天早上 8 点叫我起床」「30 分钟后提醒我开会」。系统通过自然语言理解（NLU）解析出对应的触发时间，输出统一 JSON，并在到点时通过浏览器通知 + 铃声提醒。

核心价值：零学习成本、口语化交互；相比传统「滚轮子选时间」的闹钟，输入效率更高、更自然。可作为独立工具，也可作为其他 Agent 的「定时提醒」能力模块。

形态建议：纯前端 Web 应用（H5），进阶为 PWA（可安装、可离线、可后台），避免服务端成本。这与现有项目「无服务端、预留 key 位降低成本」的思路一致。

二、目标用户与使用场景

角色典型场景口语示例

三、核心能力定义（MVP → 完整）

MVP（P0，必须）

  • 自然语言输入 → 时间解析 → JSON 输出
  • 相对时间（X 分钟后/小时后）
  • 绝对时间（今天/明天/周X/日期 + 早上/下午/晚上 + 点分）
  • 单次闹钟的创建、列表、删除、启用/停用
  • 到点提醒：浏览器通知 + 铃声
  • 备注/标签（如「叫我起床」）

完整（P1/P2，迭代）

  • 重复闹钟（每天/工作日/周末/每周X）
  • LLM 兜底解析长尾口语
  • 歧义澄清交互（「早上还是晚上？」）
  • 多端同步 / 账号（需服务端）
  • 节假日/农历（春节、端午等）
  • 智能建议（相似闹钟去重）

四、自然语言时间解析能力范围（最关键）

这是整个产品的技术核心与最大价值点。下方为覆盖能力矩阵：

类别覆盖示例解析结果
相对时间「30 分钟后」「两小时后」「半小时后」「10 秒钟后」now + Δ
绝对·日锚点「今天 / 明天 / 后天 / 大后天 / 昨天」±N 天
绝对·星期「周一」「下周一」「本周三」「礼拜天」最近的下一个该星期
绝对·日期「10 月 1 日」「1 号」「2026-10-10」「2027 年春节」指定日期（已支持阳历固定+近年份农历）
时段词「凌晨 / 早上 / 上午 / 中午 / 下午 / 傍晚 / 晚上 / 深夜」小时校正（下午3点→15）
时刻「8 点」「8 点半」「8 点一刻」「8 点 20」「08:30」HH:mm
重复「每天 / 每日」「工作日」「周末」「每周一」「每3天」「隔周六 / 双周一」recurrence：daily / weekdays / weekend / weekly:N / every:N / biweekly:N
提前提醒「提前10分钟 / 提前半小时」lead_minutes，触发时间自动前移

JSON 输出规范（Schema）

成功解析

{
  "success": true,
  "raw": "明天早上8点叫我起床",
    "alarm": {
    "timestamp": 1791590400,          // Unix 秒级时间戳（UTC），便于调度/排序
    "datetime": "2026-10-10T08:00:00+08:00",
    "date": "2026-10-10",
    "time": "08:00",
    "recurrence": "none",        // none | daily | weekdays | weekend | weekly:N | every:N | biweekly:N
    "lead_minutes": 0,           // 提前提醒分钟数（0=不提前）；如「提前10分钟」=10，触发时间自动前移
    "timezone": "Asia/Shanghai",
    "label": "叫我起床",
    "enabled": true
  },
  "confidence": 0.95,
  "needs_clarification": false,
  "ambiguities": []
}

解析失败 / 需澄清

{
  "success": false,
  "raw": "待会提醒我",
  "alarm": null,
  "confidence": 0.3,
  "needs_clarification": true,
  "ambiguities": ["未识别到具体时间，请补充如『30分钟后』或『明天8点』"]
}
设计要点：① timestamp 为 Unix 秒级时间戳（UTC），直接可用于定时器/排序；② datetime 用 ISO 8601 含时区，便于人类阅读与跨端；③ recurrence 用枚举+参数，便于重复计算（weekly:N 每週N、every:N 每N天、biweekly:N 隔周N）；④ lead_minutes 支持「提前X分钟/小时提醒」，触发时间自动前移；⑤ confidence 与 needs_clarification 让前端决定是否追问，是「Agent 感」的关键。

六、非功能需求

  • 可靠性（最高优先）：闹钟到点必须触发。纯前端在标签页关闭/浏览器退出后无法保证——这是最大约束，方案见第七节。
  • 性能：解析在毫秒级完成（规则引擎本地计算）；列表与提醒调度轻量。
  • 隐私：闹钟数据默认仅存本地（localStorage/IndexedDB），不上传；仅当用户启用「云端同步/LLM 兜底」时才联网。
  • 离线：规则引擎与提醒调度应离线可用（PWA + Service Worker）。
  • 兼容性：现代浏览器（Chrome/Edge/Safari），移动端为主。

七、技术方案建议

1. NLU 引擎选型（核心决策）

方案准确率成本离线隐私适合
规则+词典
（自研/chrono 类库）		常见口语 ~90%零✅✅MVP、确定性强场景
LLM 解析长尾/复杂高每次几分到1毛❌⚠️ 文本出网兜底、模糊表达
混合（推荐）兼顾极低（缓存命中）规则部分✅规则优先生产可用
推荐：混合架构。规则引擎覆盖 80% 常见口语（零成本、离线、隐私好）；当规则置信度低或命中长尾时，再调用 LLM 兜底。LLM 仅传时间相关文本，并可对相同解析做缓存以压低成本。

2. 触发机制（解决「页面关了还能响」）

  • 双层架构（已落地）：① 本地兜底——页面存活内由前端 1 秒轮询调度，触发 Notification + Web Audio 铃声 + 应用内响铃弹窗；② 云端推送——开启「云端推送」后，闹钟同步到最小 Node 服务端（server.js），由服务端按时间通过 Web Push 下发，浏览器/标签页完全关闭也能响。
  • Service Worker：负责 PWA 安装、离线缓存，并接收 push 事件弹系统通知；前台已聚焦时跳过系统通知，避免与本地弹窗重复。
  • Web Push 实现：使用 VAPID 自签名密钥（首次启动自动生成 data/vapid.json），依赖 web-push 库；客户端订阅经 /api/register 上报，闹钟经 /api/alarm 登记，服务端每秒调度发送。
  • 已验证：调度→Web Push 发送→异常处理链路已在本地跑通（含过期/错过保护：宕机超 2 分钟视为错过不再补发）。
  • 运行要求：Web Push 与 SW 需 localhost 或 HTTPS；本地用 node server.js 托管本页即可体验。

3. 存储与框架

  • 存储：IndexedDB（闹钟列表） + localStorage（设置/权限）。
  • 框架：原生 JS / 轻量 React；原型阶段建议原生单文件，快速验证。
  • 样式：移动优先，卡片式列表。

九、交互流程（MVP）

  1. 用户在输入框说一句话 → 点击「设置」。
  2. 前端调用 NLU 引擎，得到 JSON。
  3. 若 needs_clarification：展示澄清问题（如「早上还是晚上？」）并等待补充。
  4. 否则展示「解析卡片」预览（时间 + 标签 + 重复），用户确认。
  5. 确认后写入存储，加入提醒调度；列表展示「下次响铃：…」。
  6. 到点：通知 + 铃声；用户可「再睡一会（延时）」或「关闭」。

十、关键风险与权衡（评估核心）

低
Web 闹钟可靠性（已缓解）。原风险：页面/浏览器关闭后纯前端无法触发。现通过「Web Push + 最小服务端」解决——浏览器关闭时由服务端推送提醒；页面存活内由本地调度兜底。
残留限制：服务端进程需保持运行；公网部署需 HTTPS；移动端浏览器极端情况下仍可能限制后台推送（行业共性），必要时再上原生壳。
中
NLU 长尾准确率。规则覆盖常见口语，但「大概八点左右」「吃完饭叫我」等难覆盖。
缓解：混合架构 + 澄清交互；用原型积累语料。
中
通知权限。用户拒绝授权则完全无法提醒。
缓解：首次引导授权，拒绝时降级为「应用内提示 + 声音」。
低
时区/夏令时。中国大陆无夏令时，影响小；跨时区差旅场景需显式处理。
缓解：存储时区，默认 Asia/Shanghai。
低
重复语义边界。「工作日」= 周一至周五、「周末」= 周六日，需明确。
缓解：枚举化，文档约定。

十二、结论与建议

建议：Go（可行） 技术风险可控，核心价值清晰，且与「无服务端、低成本」定位契合。

分步推进：

  • 第一步：NLU 规则引擎 + JSON 输出（已完成，含 timestamp，附交互原型）。
  • 第二步（MVP）：闹钟列表/存储/PWA 触发（已完成）；可靠性 P0 已通过 Web Push + 最小服务端落地——浏览器关闭也能响。
  • 第三步（增强，已完成）：LLM 兜底解析长尾口语（/api/parse）+ 多轮澄清对话（Agent 感）+ 公网 HTTPS 部署脚手架（deploy/）。
  • 第四步（开放 API，已完成 Phase 1）：对外暴露 /v1/parse（NL→JSON）+ /v1/health，API Key 鉴权 + 限流 + CORS + 标准错误，附 openapi.yaml 契约与集成测试。
  • 当前状态：核心闭环 + 开放解析能力均已可用；下一步建议做文档基线对齐与 HTTPS 真机验证（确认"关浏览器也响"在真机成立），再决定单用户体验打磨 or 平台化深化。

13.2 三个关键决策点

决策
① 定位冲突：当前「无服务端、低成本」是核心卖点；多端同步（项 7）需引入账号与服务端，会打破该定位。建议：除非明确要做平台，否则暂缓。
决策
② 可靠性终局：Web Push 已覆盖绝大多数桌面/锁屏场景；若移动端有「必响」强刚需，原生壳（项 6）是更稳解法，但成本更高。
决策
③ LLM 成本边界：混合架构把 LLM 调用压到长尾（<20%），人均成本可控；若全部走 LLM，成本与延迟都会显著上升。
决策
④ 定位再校准：原文档强调"无服务端、低成本"，但开放 API 已引入服务端 + 密钥体系（Phase 1 仅解析、无存储；若推进 Phase 2 则需 DB/账号）。这实际在把项目从「自用闹钟工具」悄悄推向「定时能力开放平台」。建议先明确主形态，再决定 Phase 2 与项 7（多端同步）是否启动。
